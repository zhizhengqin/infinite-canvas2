# 洋子 B/S 与无限画布媒体服务整合设计

## 1. 意图

把用户现有的 AIStudioYangZi V2.1（包内版本 0.1.35）桌面创作流程改造成浏览器访问的单用户系统，并复用当前由 Skill 驱动、通过无限画布 MCP 执行媒体生成的工作方式。

先在本机 Docker Desktop 做完整验证，再以同一套容器化结构部署到外网 Linux 服务器。本地验证环境为 linux/arm64；外网服务器的 CPU 架构尚未提供，部署前需确认并构建对应镜像。

## 2. 用户已确认的需求

- 完整流程包括：剧本、资产、分镜、提示词、视频生成。
- 生图、生视频和视频超分都要可用。
- 继续用现有 Skill 控制创作流程和阶段确认，不改成另一套固定硬编码流程。
- 保留并整合用户现有的生图、生视频和超分渠道。
- 无限画布一起迁移到服务器，作为洋子的媒体执行服务。
- 主要通过第三方 AI API 生成，不在服务器运行本地大模型，不做批量视频处理。
- 首版为单用户系统；先本地验证，再部署外网 Linux。

## 4. 目标架构

```text
用户浏览器
  │ HTTPS（外网）或 HTTP（本机验证）
  ▼
入口与单用户鉴权
  ├──────────────► 洋子 Web + 应用后端
  │                  ├─ 项目、阶段、Skill、提示词和任务状态
  │                  └─ MCP 客户端
  │                         │ 私有 Docker 网络
  │                         ▼
  └──────────────► 无限画布 Web / Canvas Agent 媒体服务
                     ├─ 服务端媒体 MCP 工具
                     ├─ 渠道适配与任务持久化
                     └─ 素材与结果存储
                            │
                            ▼
                     第三方生图、生视频、超分 API
```

核心边界：洋子负责创作流程和项目状态；无限画布负责媒体能力、渠道执行、媒体任务和结果资产。两边都提供浏览器界面，但洋子是首版主工作台。

不采用无头浏览器模拟点击作为媒体执行引擎。现有画布 MCP 工具继续服务交互式画布；新增的服务端媒体工具不依赖用户打开某个网页。

## 5. 洋子改造

### 5.1 服务端启动

- 复用现有静态网页和 HTTP 应用工厂，新增不加载 Electrobun 窗口、菜单、FFI 和桌面更新器的 Linux 启动入口。
- 使用 Linux 对应架构的 Bun/Node.js、Python 和必要的 FFmpeg；不使用 DMG 中的 Mach-O 文件。
- `TOONFLOW_DATA_DIR` 指向持久化数据目录；服务器工作区限制在 `data/workspaces`。
- 桌面文件选择、剪贴板、保存对话框替换为浏览器上传、下载和服务端工作区选择。
- 首版关闭无法安全迁移的桌面专有入口，不用空成功响应伪装可用。

### 5.2 创作流程

沿用用户确认的现有 Skill 包和洋子阶段状态，不在平台外另建一套冲突的流程定义。

Skill 由洋子内置 Agent 配合用户在服务端配置的文本模型 API 执行，不要求本机 Kimi Code/Codex CLI，也不把交互式桌面 CLI 作为服务器依赖。

必须串联：

1. 创建或打开项目，读取当前 Skill、阶段和版本。
2. 剧本创作、草稿回传和用户确认。
3. 资产规划，以及通过媒体服务生成、上传、选择图片资产。
4. 分镜和镜头相关资产关联。
5. 视频提示词生成、保存和确认。
6. 选择视频渠道与模型，提交生成，查询原任务并保存结果。
7. 对已有视频选择超分渠道，提交超分并保存新资产版本。
8. 在项目中查看、下载和继续使用生成的图片与视频。

真实生成、采用成果和阶段推进遵循 Skill 原有确认要求。失败不自动重新提交收费任务。

### 5.3 源码策略

用户已确认目前只有 DMG，没有洋子原始源码或官方 Linux/服务器版本。因此本地阶段明确定位为**基于解包构建产物的可行性验证**，按可丢弃原型管理，而不是把压缩 bundle 当作正常源码工程直接推向生产。

本地验证优先复用完整静态前端和已有 HTTP 应用工厂，只对服务端入口及必要适配做最小修改。若关键流程无法通过局部适配打通，应报告阻塞，不用大规模不可维护的二进制改写掩盖问题。

外网上线前必须单独完成可维护性与权利评审；若无法确认关键模块可维护或无权修改部署，应暂停上线并先取得源码或授权。本地原型进入生产代码库属于后续单独决定。

## 6. 无限画布媒体服务改造

### 6.1 服务端媒体执行层

在 Canvas Agent 现有 TypeScript/Express/MCP 结构中增加服务器模式，复用无限画布已有渠道定义和协议逻辑。

需要把浏览器相关逻辑拆成：

- 可共享的协议、请求构造、响应解析、任务状态和模型能力定义。
- 浏览器专用的 IndexedDB、DOM、界面和本地存储适配。
- 服务端专用的文件、凭据、任务存储和 HTTP/MCP 适配。

优先复用 `web/src/services/api/` 中现有实现和测试，不重新手写已支持的渠道协议。

### 6.2 新增服务端 MCP 能力

提供稳定的媒体工具接口，名称可在实现计划中按项目规范确定，语义至少覆盖：

- 列出已启用的渠道、模型及 image/video/upscale 能力。
- 创建媒体任务：能力、模型、提示词、参数、素材引用和幂等键。
- 查询任务状态：保留供应商原始任务 ID 和最近确认状态。
- 取消平台侧等待；是否取消供应商任务取决于渠道真实能力，不能伪报已取消。
- 读取任务结果和资产地址。
- 上传、读取和删除受管理的媒体资产。

为服务器间调用增加带鉴权的 Streamable HTTP MCP 入口，或等效的私网 MCP 适配。不得把无鉴权的 stdio 管理接口直接暴露到公网。

### 6.3 任务与结果

每个任务至少保存：内部任务 ID、项目 ID、能力、渠道和模型、参数、素材引用、供应商任务 ID、状态、错误、创建/更新时间和结果资产 ID。

- 创建任务必须支持幂等，网络重试不得重复生成。
- 服务重启后根据供应商任务 ID 恢复查询，不新建任务替代原任务。
- 页面刷新或服务重启后仍能查看任务和结果。
- 结果文件进入服务端资产存储；洋子保存资产引用，不重复保存多份大文件。
- 超分是独立的视频任务类型，输入为已有视频资产，输出为新版本资产。
- 不设置新的全局超时、轮询间隔、重试次数、大小限制或并发上限；优先沿用各渠道现有值。若确需调整，先另行取得用户确认。

### 6.4 自定义渠道与凭据

- 保留现有自定义模型脚本和渠道配置能力。
- 服务端脚本只接受单用户管理员明确配置的受信任脚本，不开放公共上传执行。
- 脚本通过受限 HTTP 助手调用渠道，不向脚本暴露 Docker Socket、宿主机目录或无关环境变量。
- API Key 通过服务端秘密配置或 Docker Secret 注入；任务参数、日志、MCP 返回和导出文件不得包含明文密钥。
- DreamMaker 等 OAuth 账号会话按项目现有规则续期；不把访问令牌当长期 API Key，不通过导出配置复制账号会话。
- 浏览器直连和本地代理逻辑保留给原有本地模式；服务器模式使用服务端请求适配，避免把服务器凭据下发到浏览器。

## 7. 数据与现有环境迁移

使用独立持久化卷或绑定目录，至少区分：

- 洋子：设置、项目、Skill、草稿、任务关联。
- 无限画布媒体服务：渠道元数据、媒体任务、素材和结果。

本机验证使用新容器、新端口和独立数据卷，不替换或停止用户当前使用的 `infinite-canvas-kimi` 及其他无关容器。

现有浏览器数据采用显式导出/导入或一次性迁移工具：

- 迁移用户确认需要的画布、素材、生成记录和渠道元数据。
- 密钥不进入普通导出文件；在服务端重新录入或通过安全秘密配置提供。
- 迁移前记录数量和可读性检查结果，失败不覆盖原数据。
- 原浏览器数据和现有容器保持可用，直到用户确认新系统验收通过。
- 首版不做持续双向云同步；迁移是一次性、可核对的切换过程。

## 8. 鉴权与网络

- 首版只支持单用户，不声称具备多租户隔离。
- 浏览器入口需要登录或等效的单用户会话鉴权。
- 本地验证可仅监听本机地址；外网必须使用 HTTPS。
- 洋子与无限画布之间使用私有 Docker 网络和独立服务凭据。
- Canvas Agent 的媒体 MCP 管理入口仅暴露给内部网络，不直接映射公网端口。
- 不把现有仅监听 `127.0.0.1` 的本机 Agent 原样当作服务器安全边界；服务器模式需要明确的来源、令牌和会话校验。
- 不使用容器内 `localhost` 访问另一容器；本地旧服务联调可用 `host.docker.internal`，最终容器间使用服务名。

## 9. Docker 组织

用一个明确的 Compose 项目组织新环境，服务逻辑上包括：

- `yoko`：洋子网页和后端。
- `canvas-web`：无限画布网页。
- `canvas-agent`：服务端媒体 MCP、任务和资产服务。
- 入口代理：可与现有 Nginx 结构复用，不额外引入无关基础设施。

镜像按目标架构构建；本地为 arm64，外网根据实际服务器选择 amd64 或 arm64。镜像中不写 API Key、OAuth 会话或用户项目数据。

本地端口避开当前 `3001`、`8000`、`8001` 及其他已占用服务；具体空闲端口属于实现细节，由 builder 在启动前检查并选择。

## 10. 验证与验收

### 10.1 自动化验证

在现有项目测试体系内增加覆盖：

- 渠道请求和响应解析的回归测试。
- 媒体任务创建幂等、查询、失败、服务重启恢复和结果读取。
- 超分任务的输入输出与版本关联。
- MCP 鉴权、参数校验、秘密脱敏和私网接口不可匿名调用。
- 洋子服务器启动、静态页面、项目与设置持久化、上传下载。
- 从剧本到视频结果的关键集成路径，第三方 API 使用可控测试替身。

遵循项目已有构建、测试和文档规则；若项目指令与更高优先级验证要求冲突，应明确报告，而不是隐瞒未验证项。

### 10.2 本机端到端验收

在独立测试项目和独立数据卷中验证：

1. 浏览器登录并打开洋子。
2. 创建项目并加载用户确认的 Skill。
3. 完成剧本、资产、分镜和提示词阶段，刷新后内容仍在。
4. 列出服务端实际可用的生图、生视频和超分模型。
5. 上传素材并生成一张测试图片，将其关联到项目资产。
6. 用测试提示词和参考资产创建一个短视频任务，刷新页面后恢复同一任务并得到结果。
7. 对该视频执行一次超分，保存并播放新结果。
8. 重启新 Compose 环境，确认项目、任务、渠道元数据和结果仍可访问。
9. 验证匿名请求、错误凭据和跨工作区路径访问被拒绝。

真实收费调用不是设计批准的隐含授权。每次实际生图、生视频或超分前，必须向用户展示渠道、模型、参数和数量，并取得当次确认；失败不自动重试或换渠道重复扣费。

### 10.3 外网切换前检查

- 确认服务器架构、磁盘、内存和域名。
- 构建并验证对应架构镜像。
- 配置 HTTPS、单用户账号、服务间凭据和秘密。
- 明确备份、恢复和日志脱敏方式。
- 用同一验收清单重新验证，不以本地成功替代外网验证。

## 11. 非目标与反目标

- 不做多用户、多租户和公共注册。
- 不运行本地大模型，不增加 GPU 或批量视频处理要求。
- 不绕过第三方登录、OAuth、安全验证、付费或访问控制。
- 不直接运行 DMG 中的 macOS 可执行文件。
- 不用无头浏览器点击代替正式媒体任务接口。
- 不覆盖现有项目、不动无关容器、不回滚用户工作区修改。
- 不为了“全流程”伪造未接通渠道或未完成任务的成功状态。
- 不将当前无限画布描述成已经具备云同步或服务端持久化。

## 12. 实施顺序

1. 建立不干扰现有环境的独立 Compose 骨架和持久化结构。
2. 为无限画布建立服务端渠道/任务适配层及媒体 MCP，先用测试替身验证。
3. 为洋子建立 Linux 服务端入口，打通项目、Skill、设置和浏览器文件交互。
4. 串联剧本、资产、分镜、提示词、视频和超分完整流程。
5. 一次性迁移全部现有画布、素材、生成记录和渠道元数据。
6. 完成本机自动化和端到端验收，再进行外网部署。

具体文件级改动、任务拆分和测试命令在用户对本文档作出明确批准后，通过实施计划确定。

## 13. 用户补充确认与设计决定

用户已进一步确认：

- 洋子目前只有 DMG；本地按构建产物可行性验证处理，生产可维护性另行评审。
- Skill 使用洋子内置 Agent 和服务端文本模型 API，不依赖本机交互式 AI CLI。
- 所有现有渠道都纳入整合；真实生成验收只要求生图、生视频、超分各选一个主渠道执行一次，其余渠道先验证配置、模型发现和接口联通。
- 一次性迁移全部现有画布、素材、生成记录和渠道元数据；秘密和 OAuth 会话仍按安全规则单独处理。

以下为设计决定，不冒充用户已经逐项同意：

- 首版以洋子为主工作台，同时保留无限画布自己的管理/编辑网页。
- 新增真正的服务端媒体 MCP，而不是依赖活跃浏览器页面。
- 优先复用现有 TypeScript 渠道模块，不另起 Python 媒体后端。
- 采用一次性显式迁移，不实现持续双向同步。
- 实施早期验证洋子 MCP 客户端能否连接带鉴权的私网 HTTP MCP；若不能，则在洋子侧增加受管理的 stdio 到私网 HTTP 适配进程，不把该兼容问题转成公网无鉴权接口。
- DreamMaker 等交互式账号渠道在服务器上通过官方流程重新授权；若官方流程不支持服务器环境，则如实标记该渠道待人工接入，不导出或绕过本机会话。

仍需用户在相应操作前提供或确认：

- 实际启用哪些现有 Skill，以及本地验收使用的文本模型 API。
- 三个真实生成验收各自选用的主渠道、模型、参数和当次授权。
- 外网服务器的 CPU 架构、域名和部署凭据；这些信息不影响本地设计，但影响最终部署。
